# Architecture

Nuxt Native's goal is React Native/Flutter for the Nuxt ecosystem: Vue
components rendered as real native views, not a WebView. This document is
the honest map of what that requires, what's implemented, and what isn't —
so contributors know exactly where the frontier is.

## Why NativeScript, not a from-scratch renderer

A "true native renderer" needs two things a WebView-based tool (Capacitor,
Ionic) doesn't: a JS runtime with native marshalling (so JS can call
`UIView`/`android.view.View` APIs directly, no bridge-over-HTTP, no WebView
process), and a Vue renderer that creates native view instances instead of
DOM nodes. Building both from scratch is most of what NativeScript itself
is — a mature, years-old project. Reinventing it would be a multi-year
detour before a single native view ever appeared on screen. Nuxt Native
builds *on* NativeScript's runtime and on `nativescript-vue`'s renderer,
and focuses its own effort on the part that's actually missing: Nuxt's
developer experience layered on top of that renderer.

## Why not Nuxt's own build pipeline (Vite/Nitro)

Nuxt's builder assumes a browser target: it generates a client entry that
mounts Vue to a DOM node, and Nitro exists to produce a server response to
hydrate. Neither applies here — there's no DOM node, and `ssr: false` on
native builds means there's no server response either. Rather than fight
Nuxt's builder internals to make it emit something it wasn't designed to
emit, Nuxt Native uses Nuxt only for what it's actually good at in this
context — file-based page discovery, the module/auto-import system, config
— and hands the actual on-device bundle to NativeScript's own webpack-based
toolchain, which already knows how to produce a native bundle correctly.

```
app/pages/*.vue  ──(pages:extend hook)──►  route manifest  ──►  useNativeRouter()
                 ──(nuxt-native CLI scan)──►  .nuxt-native/app.js  ──►  ns run/build
```

Two independent consumers read the same page tree: the Nuxt module (via
`pages:extend`, for editor/type-checking DX and the manifest `vue-tsc` sees)
and the CLI (via a standalone filesystem scan, since `init`/`dev`/`build`
run outside Nuxt's dev server). See `src/build/generate-routes.ts` and
`cli/lib/scan-pages.mjs` — they implement the same file-based routing
conventions independently on purpose, rather than sharing a runtime
dependency between a Nuxt-hooked build step and a standalone CLI process.

| Nuxt module (`src/module.ts`) | Implemented, verified | Registers composables/components auto-import dirs, disables SSR, generates the route manifest template via a real `@nuxt/kit` `pages:extend` hook. Route groups / more exotic Nuxt routing features aren't ported yet. |

Every native prop/event name used (`Switch.checked`/`checkedChange`, `TextField.hint`/`secure`/`textChange`, `ActivityIndicator.busy`, `Image.src`/`stretch`, `View.boxShadow`/`borderRadius`) was checked against `@nativescript/core`'s real `.d.ts` files first — the same discipline that caught real bugs earlier in this project. `<NBottomSheet>` has no native primitive to wrap; it's a full-screen backdrop + bottom-anchored card shown via nativescript-vue's real `$showModal`/`$closeModal` (verified against `modals.d.ts`), with your own content component passed in and rendered via `<component :is>` — `useModal()` is the same API for showing any component as a plain modal. Verified end-to-end: a demo page exercising every component (including opening a bottom sheet with a separate content component) compiled successfully with a real `webpack()` run, and the compiled bundle was confirmed to actually contain each component's template text and nativescript-vue's `$showModal` implementation — not yet run on an actual device. |

| CLI `dev` / `build` | Implemented, delegates the hard part | Regenerates `.nuxt-native/` then shells to `ns run <platform>` / `ns build <platform>`. NativeScript's own webpack + LiveSync handle the actual native compile/deploy/hot-reload — not reimplemented here. |
| The actual compiler/bundler (`webpack.config.cjs`, `.vue` → native bundle) | Implemented, partially verified | This was missing entirely until reported — `init`/`create` generated `nativescript.config.ts` and the route manifest, but no `webpack.config.js`, no `@nativescript/webpack` devDependency, and nothing wiring `vue-loader` to nativescript-vue's renderer, so `.vue` pages had no loader at all. Fixed by generating `webpack.config.cjs` that calls the official `nativescript-vue/nativescript.webpack.js` helper (it registers vue-loader against `@nativescript/webpack`'s base "vue" rule and aliases the bare `vue` specifier to `nativescript-vue`, which is what lets `import { ref } from 'vue'` resolve correctly on-device). It's `.cjs`, not `.js`, because `@nativescript/webpack` loads it with a plain `require(configPath)` (confirmed by reading its bin source) and nuxt-native projects have `"type": "module"` in package.json — under that, `require()` of a `.js` file throws `ERR_REQUIRE_ESM`; reproduced directly, then confirmed clean after renaming to `.cjs` and pointing `nativescript.config.ts`'s `bundlerConfigPath` at it. Invoking the resolved config directly (not through the real `ns` CLI, which supplies more `env` context) now produces a complete, valid webpack `entry` config correctly referencing the generated `.nuxt-native/app.js`; only a harmless "Cannot find NativeScript CLI path" warning remains, expected since we're not going through the real CLI. **Fully verified past this point**: running an actual `webpack(config, callback)` compilation (not just resolving the config object) against a fresh scaffold now completes with **zero errors**, emitting real `bundle.js`/`vendor.js`/`runtime.js` — vue-loader, ts-loader, and every native-specific transform (worker-loader, native-class-downlevel/strip-loader) all working together correctly for the first time. See the `typescript`/tsconfig row below for what else that took. |
| `typescript`/`tsconfig.json` for the native build | Implemented, verified via a real webpack compile | Three compounding bugs, found by running an actual `webpack()` compilation against a fresh scaffold (not just resolving config) after the `main` fix above got far enough to reach real `.vue` compilation: **(1)** `ts-loader` (a dependency of `@nativescript/webpack`) peer-depends on `typescript`, which was never added to generated projects — `@nativescript/webpack` only lists it in *its own* devDependencies (used to build itself, never installed transitively for consumers). Confirmed by reading `ts-loader`'s `compilerSetup.js`: when `require('typescript')` throws, it swallows the error into an unused message and presses on with `compiler` left `undefined`, crashing later on `compiler.sys.fileExists` — exactly the `Cannot read properties of undefined (reading 'fileExists')` a real user hit. **(2)** The generated `tsconfig.json` was Nuxt's usual references-only shell pointing at `.nuxt/tsconfig.*.json`, which only exists after `nuxi prepare` runs (never part of this framework's actual workflow) — useless to `ts-loader`, which reads this file directly for real `compilerOptions`. Replaced with a real, standalone config. **(3)** Two further rounds against a real compile: including `nuxt.config.ts` put it in scope for `ForkTsCheckerWebpackPlugin` (which only activates once `typescript` is an actual dependency — fix (1) turned it on), and it fails type-checking there since `defineNuxtConfig` is an ambient global only Nuxt's own generated types provide; excluded it. Then `TS18003: No inputs were found` — TypeScript's `include` glob-matching filters by a hardcoded extension list (`.ts`/`.d.ts`, plus `.js` only with `allowJs`) regardless of what the glob pattern spells, so listing `*.vue` explicitly did nothing and nothing else matched; added `allowJs: true` so the generated `.nuxt-native/app.js` counts as a root file. After all four fixes: `webpack 5.111.1 compiled successfully`, zero errors, on a fresh `create` scaffold. |
| `"type": "module"` in generated `package.json` | Fixed — removed entirely | Same real user, further downstream (the actual `ns run android` device deploy step, past a successful webpack compile): `ReferenceError: require is not defined in ES module scope` inside `platforms/android/build-tools/jsparser/js_parser.js` — a plain CommonJS script *shipped by `@nativescript/android`'s own runtime tooling*, not something this framework generates or controls. Node determines a `.js` file's module type by walking up to the nearest `package.json`; that vendored file has no closer one of its own, so it inherited `"type": "module"` from the project root and got misinterpreted as ESM. Unlike the earlier `webpack.config.cjs` fix, renaming isn't an option here — this file is regenerated by `@nativescript/android` itself on every `ns platform add`. Fixed at the root: removed `"type": "module"` from the generated `package.json` entirely. Verified safe: none of our own generated files need it (`.nuxt-native/app.js`'s `import` syntax is only ever parsed by webpack's own module system, never Node's `require`/`import`; `webpack.config.cjs` is unambiguous regardless of `"type"`) — re-ran the same real `webpack()` compile used to verify the fixes above and it still succeeds with zero errors. |
| `bundlerConfigPath` reliably reaching `ns` | Worked around, root cause unconfirmed | A real user hit `ns run android` reporting the hardcoded default `webpack.config.js` "does not exist" — despite `nativescript.config.ts` correctly containing `bundlerConfigPath: "webpack.config.cjs"` and that exact file being present. Directly replicating the CLI's own TS-parsing logic (`ts.transpileModule` + eval, same as `project-config-service.js`) against their file's content extracted `bundlerConfigPath` correctly, ruling out a parsing bug in our generated config. Leading theory: `init`/`dev`/`build` invoke `ns` via `npx --yes nativescript ...`, which resolves from npx's own cache rather than the project's `node_modules` — a stale cached CLI build predating `bundlerConfigPath` support would silently ignore it and fall back to the default, matching the error's exact wording (the fallback branch, not the one used when a custom path is recognized). Fixed pragmatically either way: `nativescript.config.ts` now also sets the older `webpackConfigPath` field to the same path — `bundlerConfigPath` falls back to it internally, so an outdated CLI that only understands the older field still resolves correctly. Not fully root-caused: haven't confirmed which npx-cached version the reporting user actually had. |
| `main` entry field (nativescript.config.ts + package.json) | Implemented, verified | Same real user, next error after the above fix: `@nativescript/webpack`'s `getEntryPath()` tries `nativescript.config.ts`'s `main` field, then `package.json`'s `main` field, then calls `path.resolve(root, undefined)` if neither is set — throwing `TypeError [ERR_INVALID_ARG_TYPE]`. Neither field was ever set. Read `getEntryPath()`'s and `getProjectRootPath()`'s source directly to confirm `main` resolves relative to the project root (`process.cwd()`), not `appPath`. Fixed by setting `main: '.nuxt-native/app.js'` in both generated files (the constant now lives in `generate-entry.mjs` as `ENTRY_FILE`, imported by both, so the path can't drift out of sync between them). Verified by invoking the generated `webpack.config.cjs` directly on a fresh scaffold: it now resolves to a complete `entry` object correctly listing `.nuxt-native/app.js`, where it previously threw immediately. |
| Components global registration (`<NPage>` etc.) | Fixed | Same real user's device run — this got past `webpack.config.cjs`/`typescript`/`type:module` and past `ns run android`'s full build+install+launch (first time the app has actually run on a physical device), then crashed at Vue's `setup()` with `ReferenceError: useDevice is not defined`. Two separate gaps surfaced by this: components had no registration mechanism at all in the native bundle (Nuxt's `addComponentsDir` only registers globally for Nuxt's *own* build, which the native path never goes through), and composables had no auto-import either (see next row). Fixed the component half: the generated `.nuxt-native/app.js` bootstrap now imports `<NPage>`/`<NActionBar>`/`<NTabs>` from a new `nuxt-native/runtime/*` subpath export and registers them globally via `createApp(...).component(...)`, mirroring what Nuxt's own auto-registration does — the same mechanism (Vue's app-level component registry), just invoked directly. Verified end-to-end after pushing: fresh `create`, real npm install of the pushed package, then a real `webpack()` compilation against the actual installed `node_modules/nuxt-native` (not local files) — compiled successfully, zero errors. **Then confirmed on the reporting user's real device**: the app built, installed, launched, and rendered correctly. |
| Auto-imports reaching the on-device bundle | **Partially addressed, still open for user-authored pages** | The other half of the crash above: composables (`useDevice`, `useNativeRouter`, etc.) have no auto-import in the native bundle either — `addImportsDir` only covers Nuxt's own build. Full fix (wiring `unplugin-auto-import`'s webpack plugin into `webpack.config.cjs`, matching what Nuxt does for its own build) is not done. Stopgap shipped: the generated demo pages (`indexPage()`/`detailsPage()` in `scaffold-templates.mjs`) now use explicit `import { useDevice } from 'nuxt-native/runtime/composables/useDevice.js'`-style imports instead of relying on auto-import — this fixes *our own* scaffolded demo, but any page a user writes themselves still needs the same explicit-import pattern until real auto-import wiring lands. |
| `#build/nuxt-native/route-manifest.mjs` alias | Fixed, verified via real webpack compile | Surfaced by testing the fix above before shipping it, not by a user report: `useNativeRouter.ts` imports its route table from `#build/nuxt-native/route-manifest.mjs` — `#build` is a Nuxt-internal alias Nuxt's *own* Vite/webpack build registers (resolving to `.nuxt/`), which the native build never goes through, so the specifier had no way to resolve at all: `Module not found: Can't resolve '#build/nuxt-native/route-manifest.mjs'`. Fixed by adding a `webpack.chainWebpack` alias in the generated `webpack.config.cjs` mapping that exact specifier to the project's own CLI-generated `.nuxt-native/route-manifest.mjs` — the same composable source now resolves correctly in both Nuxt's build and the native one, no fork needed. Verified via a real `webpack()` compile against the actual installed package: compiled successfully, and correctly code-split `details/[id].vue` into its own chunk, confirming the manifest's dynamic `import()` resolves too. |
| End-to-end device/emulator testing | **Not done** | Nothing in this repo has been run against a real iOS/Android build yet — there's no mobile toolchain in the environment this was authored in. Treat the `ns`/NativeScript integration points as a well-reasoned first draft, not a verified one. |

## Roadmap

1. Get a real Android SDK or Xcode install in front of this so `ns platform
   add` can finish (it's the one thing that genuinely can't be automated
   here) — then `ns build android` is the real end-to-end test of
   `webpack.config.cjs` and everything upstream of it. High odds it surfaces
   another gap the same way the missing webpack config and its `.cjs`
   requirement did; treat that as expected, not a sign anything above is
   unreliable.
2. Wire `unplugin-auto-import`/`unplugin-vue-components` into the
   NativeScript webpack build the CLI hands off to, so auto-imports work
   identically in editor DX and on-device.
3. Expand the native-aware UI kit (lists, action sheets, modals, tab
   navigators) past the current `<NPage>`/`<NActionBar>`/`<NTabs>` set.
4. Port more of Nuxt's file-based routing conventions (route groups,
   layouts-equivalent) into `generate-routes.ts`/`scan-pages.mjs`.
5. CI: a real device-farm or simulator smoke test, once (1) is verified.
6. Publish to npm once (1)-(3) are further along. Until then, install from
   `github:vastx-tech/nuxt-native` (see README) — that install path only
   works at all because `package.json` has a `prepare` script that runs
   `nuxt-module-build build`; `npm install`'s git-dependency flow runs
   `prepare`, not `prepack` (verified by installing the pushed repo into a
   scratch project and checking what actually landed in `node_modules`).
